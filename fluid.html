🌊 How it works

The Equations Behind Every Puff of Smoke

Everything you see — the swirls, the tendrils, the way smoke curls around your cursor — is computed by the Navier-Stokes equations, a pair of partial differential equations that have described how fluids move since 1822. Every weather forecast, every animated ocean in a movie, and every CFD simulation of an aircraft wing uses some form of these same equations.

The simulation uses a method published by Jos Stam in 1999 called "Stable Fluids". Before Stam, real-time fluid sims would explode — tiny numerical errors would amplify each frame until the simulation produced nonsense. Stam's insight was to use an implicit integration method that is unconditionally stable, meaning it can never blow up regardless of how large the timestep is. The tradeoff: it slightly over-diffuses (smooths out) fine vortices. That's why the smoke looks soft rather than sharp.

Step 1

Add Forces

Your mouse drag adds velocity directly to the grid. The fluid accelerates where you push it.

Step 2

Diffuse

Viscosity spreads velocity to neighbours. Solved with 20 Gauss-Seidel iterations — the same iterative algebra used in engineering solvers.

Step 3

Advect

Trace each grid point backwards through the velocity field to find where it came from. Sample density/velocity at that origin. This is "semi-Lagrangian" advection.

Step 4

Project

Enforce that fluid is incompressible: what flows in must flow out. Solved via a Poisson pressure equation — this creates the characteristic swirling vortices.

How professional software really solves this

This simulation uses a 128×128 grid (about 16,000 cells) solved entirely in the browser. A production CFD solver like OpenFOAM or Ansys Fluent might use 10 to 100 million cells, adaptive mesh refinement (smaller cells where gradients are steep), a multigrid pressure solver that converges in microseconds instead of 20 iterations, and turbulence models (k-ε or LES) that capture sub-grid-scale eddies we can't directly resolve. Real weather models (like ECMWF's IFS) add a spherical-coordinate domain, 137 vertical atmospheric layers, and physics parameterizations for clouds, radiation, and ocean surface fluxes. The math is the same; the resolution and physics packages are not.

How this is built — technical details

The fluid solver runs in a Web Worker completely off the main thread. The grid arrays (vx, vy, density) are passed as Transferable ArrayBuffers — zero structured-clone overhead per frame.

The main thread writes one pixel per grid cell (N×N ImageData), then scales that bitmap to the viewport with drawImage. A second canvas under the sharp pass uses CSS blur as a cheap bloom. That is not a HDR threshold bloom from film compositors — it is a glow of the same density field.

GPU GPGPU (ping-pong float textures for the Stam steps) was not shipped. WebGL2 float framebuffers are inconsistent on mid-range phones, and an unstable solver is worse than a worker that holds 30–60 fps at 64–128². The solver stays on the CPU worker.

Grid resolution is auto-detected: 128×128 on desktop (satisfies 60fps), 96×96 or 64×64 on low-power devices (battery saver or GPU score below threshold). The switch is based on a warm-up framerate measurement over the first 60 frames.

Configuration is persisted in the URL as ?visc=…&diff=…&decay=…&color=…&preset=… so any configuration is shareable. The Share button copies the current URL to clipboard.
